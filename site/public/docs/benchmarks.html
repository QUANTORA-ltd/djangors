Djangors Documentation

Honest HTTP benchmarks

These are measurements, not performance claims inferred from language reputation. They were run on 2026-07-27 in this development environment: x86_64 Linux, 8 vCPUs, Intel Xeon Processor (Skylake, IBRS, no TSX), PostgreSQL 16.14 on the same machine, Rust 1.96.0, axum 0.8.9, Django 6.0.7, Gunicorn 26.0.0, and oha 1.15.0. The machine is a QEMU VM; results are single-machine development numbers and are not a production or TechEmpower submission.

Targets and fairness

The Djangors target is examples/polls, with a new /hello/ view returning Hello, world! and its existing / view. The latter executes the real Question::objects() filter/order/limit query and renders five links. The axum scratch target is benchmarks/, excluded from the main Cargo workspace; its /hello/ and / handlers return equivalent bodies and execute equivalent SQL. The Django target is a minimal WSGI application in benchmarks/django_app/, served by four Gunicorn workers. Its / view executes the same SQL. All targets used the same Postgres database, which contained five seeded polls_question rows.

The hello path is deliberately routing/response only. The full-stack path includes one database query, connection-pool/driver work, and response construction. Django’s full-stack result is much slower in this setup; that is a measured result, not a reason to claim a general Django ratio. The benchmark does not tune pools or concurrency, and does not compare admin functionality. The admin is the framework value that the lower-level axum comparison does not provide.

JSON Serialization Benchmark (Compile-Time write_json vs Axum, Gin, Fastify, FastAPI)

To measure the impact of Djangors’s compile-time direct JSON writer (#[derive(Model)] generating Model::write_json, exposed via serialize_to_vec / serialize_many_to_vec and Response::json_bytes), we ran a dedicated HTTP JSON serialization benchmark across five frameworks on the same machine (8-vCPU Intel Core i5-8350U @ 1.70 GHz, Linux 7.0, 32 concurrent HTTP/1.1 keep-alive connections, 1s warmup + 5s measurement per endpoint).

Each framework served two endpoints with an identical 7-field BenchItem model (id: i64, name: String with quotes/ampersands requiring JSON escaping, category: String, price: f64, in_stock: bool, tags_Summary: String, created_at: DateTime<Utc>):

  1. /json/single (~190 B JSON object): Serializes 1 model instance per request.
  2. /json/list (~9.5 KB JSON array): Serializes a 50-item Vec<BenchItem> per request.

Key Takeaways

  • +70.6% faster 50-item list serialization inside Djangors: Switching from djangors_rest::serialize (serde_json::Value tree allocation) to compile-time Model::write_json (serialize_many_to_vec + Response::json_bytes) jumped 50-item list throughput from 7,390 req/s to 12,611 req/s (and cut p50 latency from 4.08 ms to 2.34 ms).
  • Parity with (and ahead of) Axum on list payloads: On single objects, Djangors (18,961 req/s) and Axum (18,905 req/s) are neck-and-neck because HTTP/1.1 framing dominates. On 50-item lists where JSON serialization is a larger share of CPU time, Djangors’s pre-sized Vec::with_capacity(items.len() * 128) + compile-time static key writers (itoa/ryu + fast string escaping) achieved 12,611 req/s (116.94 MiB/s) vs Axum’s 9,957 req/s (89.96 MiB/s) (+26.6%).
  • 2.0x Gin (Go), 4.1x FastAPI (Pydantic v2), and 5.0x Fastify (fast-json-stringify) on 50-item lists: Note that Fastify runs on a single Node.js event-loop thread by default whereas Rust (Tokio), Go (goroutines), and FastAPI (4 Uvicorn workers) utilize multiple cores.
